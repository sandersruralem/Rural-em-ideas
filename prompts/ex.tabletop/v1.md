# Prompt: `ex.tabletop`

| Field | Value |
| --- | --- |
| **ID** | `ex.tabletop` |
| **Version** | v1 |
| **Status** | Draft — untested |
| **Job** | Build a discussion-based tabletop exercise package, and later draft its after-action report |
| **Recommended tool** | Claude Pro for Mode A; Microsoft Copilot for Mode B when notes are not yet public |
| **Data level** | Green, or Yellow in Copilot once authorized. Never Red. |
| **Reviewer** | Emergency Manager or equivalent, plus the exercise lead |

Job playbook: [tabletop-exercise.md](../../docs/job-playbooks/tabletop-exercise.md)

---

## When to use

Designing a tabletop for county staff, volunteer fire and EMS, road department, schools, or the
LEPC. Mode B drafts the after-action report from notes taken during the exercise.

## When not to use

- For full-scale or functional exercises with live field play
- For an evaluated exercise tied to a grant deliverable, without first confirming the required format
  with the state exercise officer
- For any scenario built on a real incident involving identifiable people

## Required inputs

| Input | Source | Notes |
| --- | --- | --- |
| County fact pack | `context/county-fact-pack.md` | Always |
| Hazard and premise | Hazard mitigation plan | Must be plausible here |
| Exercise length | Exercise lead | Typically 90–120 minutes |
| Participants | Exercise lead | By position, never by name |
| Capabilities to exercise | Exercise lead | Communications, mass care, warning, resource management |
| Season and time of day | Exercise lead | Drives everything in a rural scenario |
| Local constraints | Emergency Manager | Volunteer staffing, single access routes, no local hospital |

## Optional inputs

| Input | Effect |
| --- | --- |
| Objectives | If omitted, the prompt proposes them |
| Prior corrective actions | Lets the exercise retest open findings |
| Number of modules | Defaults to three |

## System block

```text
You are assisting a small rural county emergency management office in the United States
with exercise design and after-action documentation.

Rules that apply to every response:
- Use only the information provided. Do not assume urban resources. Unless the fact pack
  says otherwise, assume volunteer fire and EMS, limited staffing, long travel distances,
  no local hospital, and limited mutual aid availability.
- Every person, business, and organization in a scenario must be obviously fictional.
  Never use a real resident, business, school, or facility name.
- Never invent county capabilities, equipment, agreements, or staffing that were not
  provided. If a needed fact is missing, write UNKNOWN and list it under "Information
  Needed."
- Objectives must be measurable: each states an observable outcome and how a facilitator
  would know it was achieved.
- Inject timing must fit the stated exercise length with room for discussion. Assume
  discussion runs long.
- After-action findings must come from the notes provided, not from general best
  practice. Every corrective action needs an owner role and a due date field.
- Do not include personal, medical, or law-enforcement information even if it appears in
  the input. If you see any, stop and say so instead of processing it.
- This is a draft for human review, not an approved exercise document.
- Follow the output structure exactly. Do not add sections or commentary.
```

## User block — Mode A: design the exercise

```text
Design a discussion-based tabletop exercise for our county.

COUNTY FACT PACK:
<paste the county fact pack>

HAZARD AND PREMISE:
<for example: ice storm with extended power outage>

SEASON AND TIME OF DAY:
<for example: late January, onset overnight>

EXERCISE LENGTH:
<minutes>

NUMBER OF MODULES:
<default 3>

PARTICIPANTS (by position):
<for example: emergency manager, road superintendent, volunteer fire chief, EMS
director, school superintendent, county clerk, dispatch supervisor>

CAPABILITIES TO EXERCISE:
<for example: operational communications, mass care, public warning>

OBJECTIVES:
<list two to four, or write "propose objectives">

LOCAL CONSTRAINTS:
<for example: all volunteer fire, no hospital in county, single highway through town>

PRIOR CORRECTIVE ACTIONS TO RETEST:
<paste, or write "none">

OUTPUT FORMAT:
1. Exercise Overview — purpose, scope, participants, length
2. Safety and Artificiality Statement
3. Objectives — table: Objective | Capability | How success is observed
4. Scenario Narrative — 200 to 400 words, fictional names only
5. Module Breakdown — for each module: situation update, timing, and three to five
   discussion questions
6. Inject Schedule — table: Time | Inject | Intended discussion | Delivered to
7. Facilitator Notes — expected discussion points and likely sticking points
8. Information Needed — what was missing from these inputs
```

## User block — Mode B: draft the after-action report

```text
Draft an after-action report from the notes below. Use only what the notes contain.

COUNTY FACT PACK:
<paste the county fact pack>

EXERCISE OVERVIEW:
<name, date, hazard, participants by position, objectives>

NOTES FROM THE EXERCISE:
<paste raw notes; remove any real resident or patient information first>

OUTPUT FORMAT:
1. Exercise Summary — what was run and who took part
2. Objective Performance — table: Objective | Performed / Partially / Not performed |
   Evidence from the notes
3. Strengths — with the note that supports each
4. Areas for Improvement — with the note that supports each
5. Corrective Actions — table: Action | Owner role | Due date | Capability
6. Information Needed — gaps in the notes that block a complete report
```

---

## Expected output schema

Mode A: Exercise Overview, Safety and Artificiality Statement, Objectives, Scenario Narrative,
Module Breakdown, Inject Schedule, Facilitator Notes, Information Needed.

Mode B: Exercise Summary, Objective Performance, Strengths, Areas for Improvement, Corrective
Actions, Information Needed.

## Acceptance criteria

**Mode A**

- [ ] Scenario is plausible for this county's hazards, geography, season, and staffing
- [ ] Every proper noun in the scenario is fictional
- [ ] Two to four objectives, each with an observable success measure
- [ ] Inject count and timing fit the stated exercise length with discussion room
- [ ] Scenario narrative is 200 to 400 words
- [ ] No urban assumptions: no transit, no multiple hospitals, no large career departments,
      unless the fact pack says so
- [ ] No invented county capability, equipment, or agreement
- [ ] Safety and artificiality statement present
- [ ] Output matches the schema exactly

**Mode B**

- [ ] Every finding traces to a specific note
- [ ] No finding is generic best practice unsupported by the notes
- [ ] Every corrective action has an owner role and a due-date field
- [ ] Objective performance ratings match the evidence cited
- [ ] Gaps in the notes appear under Information Needed
- [ ] Output matches the schema exactly

## Review checklist

Applied in addition to the [universal checklist](../../docs/review-checklist.md), sections A and D.

- [ ] Scan every proper noun for real people, businesses, and facilities
- [ ] Confirm the season and geography match this county
- [ ] Count injects against available minutes
- [ ] Confirm each objective could actually be observed in a discussion-based format
- [ ] For Mode B, confirm findings match what happened in the room
- [ ] Assign a real owner and date to each corrective action before filing

## Known failure modes

| Failure | How to catch it |
| --- | --- |
| Urban assumptions | Look for transit, multiple hospitals, large career staffing |
| Real business or resident names | Scan every proper noun |
| Too many injects for the time | Count injects against minutes and cut |
| Unmeasurable objectives | Reject any objective without an observable outcome |
| Findings drift to generic best practice | Require a supporting note for each finding |
| Corrective actions with no owner | Reject the draft |
| Wrong season for the hazard | Check against the stated season |
